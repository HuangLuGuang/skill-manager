# AIDR 审计持锁与共享准入：100 客户端混合负载对照

本轮修复审计/列表持写锁期间的重复读取，并让后台审计与采集共享两个异步准入名额。最终低、高负载各三组成对对照，共 12 轮，另有两轮独立诊断。高负载唯一 ACK 吞吐中位值提高 2.2%、窗口末积压减少 13.6%、Skill 列表 P95 下降 23.3%；低负载模型 P95 三组均下降，审计最终首次未核对数全部保持为零。

这不代表所有指标通过：低负载列表/概览 P95 中位值仍分别升高 3.3%/6.4%；高负载模型 P95 中位值基本持平，但其中一组模型和 MCP 明显升高。高负载审计待复核数 P95 略增，最老超期仍约 1 秒。总体保留了审计追赶改善，但不能宣布所有页面与网关尾延迟均无回退。

数据库继续使用 SQLite，模型网关代码未修改；未提交、推送或部署。

## 已确认的等待来源与修复

诊断拆分异步准入、共享线程排队、连接池等待、写锁获取和持锁处理。正式性能矩阵不带插桩，避免把插桩开销混入吞吐与 P95 结论。

1. **持写锁期间重复 SELECT。** 原审计核对每更新一条用量便将 ORM 对象过期，随后读取身份字段触发完整用量重读，再逐条查询旧告警。十条列表核对在持锁期间执行二十次 SELECT；后台同样每条两次。现在条件更新成功后同步本次写入值，条件失败时仍重读当前记录；旧告警在本组第一次成功更新取得写锁后统一查询。准备期间并发新提交的告警仍能被看到，结论、历史、告警保持一起提交或回滚。
2. **审计额外竞争采集写锁。** 原两路采集之外，后台审计独立进入工作线程竞争 SQLite 写锁。现在审计与采集共享当前事件循环的两个异步名额，先排队再进入工作线程。审计仍每批最多 50 条、独立提交，保留每轮最多四批、0.5 秒协作预算和原忙/闲等待；不会在认证计算或提交中途强制中断。取消时通过已有的屏蔽取消工作函数等事务完成后再释放名额。
3. **准入交接竞态。** 在本机 AnyIO 4.13.0 的 CapacityLimiter 路径中，两个名额偶尔出现三个占用者：释放时唤醒等待者后、等待者恢复之前，新任务可以抢占尚未登记的名额。回归测试用固定交接顺序复现峰值 3。资源准入改为 `Semaphore(2, max_value=2)`，在唤醒时保留名额；同一测试峰值为 2，最终诊断中的实际占用也从未超过 2。这个门控控制本进程资源占用，凭据授权并发和跨进程幂等仍由原数据库校验保证。没有升级依赖或修改数据库结构。

最终诊断补传窗口的 P95：

| 路径 | 获取写锁 ms，前 → 后 | 持锁处理 ms，前 → 后 | 线程排队 ms，前 → 后 |
| --- | ---: | ---: | ---: |
| Skill 后台审计 | 146.43 → 186.30 | 43.89 → 19.63 | 1.46 → 1.64 |
| Skill 列表 | 120.39 → 368.48 | 18.81 → 7.27 | 2.90 → 3.29 |
| 日志持久化 | 132.64 → 104.55 | 13.03 → 12.03 | 1.10 → 1.00 |
| Hook 持久化 | 129.09 → 92.83 | 10.76 → 9.42 | 1.03 → 0.98 |
| 模型完成阶段 | 164.03 → 153.35 | 11.19 → 13.25 | 2.64 → 1.69 |

后台审计和列表持锁处理段分别下降约 55.3%、61.4%，但并非所有路径拿锁等待都下降。审计新增异步准入等待 P95 为 254.19ms，发生在工作线程及数据库连接之外。上述路径连接池等待 P95 通常不足 1ms，证据不支持通过扩大线程池解决当前问题。

持锁处理段不包括物理提交 I/O；物理提交单独记录。不同分布的 P95 不能相加。诊断只有一组成对样本，且显式获取写锁会改变运行开销，因此不能用诊断轮次的页面/网关 P95 代替正式结果，也不能将所有尾延迟唯一归因于上述两类开销。

## 对照基线、负载与环境

分支 `RENA-1470`，HEAD `eeee22bc312991b64d4c54c8da4fb30c2596a925`，保留此前未提交修改。基线是本轮开始时的工作区，已经包含上一轮 AIDR 证据索引和追赶调度，以及此前网关、Dify Session、幂等和并发回归修复。最终两版本应用代码仅 `backend/aidr_skill_usage.py` 与 `backend/services/aidr_ingest.py` 不同，逐轮源码摘要一致，模型网关及数据库模型/迁移文件相同。

沿用 [上次复测](2026-10-17-aidr-evidence-catchup.md) 的外部负载参数：100 个客户端身份、4 路上传、每批日志/Hook 各十条、正文 1,024 字节，客户端 outbox fsync，故意忽略部分成功 ACK 后按相同字节重传。单 Uvicorn worker、SQLite WAL。服务端准入配置仍为两个名额，本轮明确将审计纳入共享范围并修复交接竞态，这是被测应用变化。

每轮基准 20 秒、持续采集 30 秒、断网 20 秒、补传与清理 60 秒、恢复 20 秒，随后最多排空 120 秒。低负载日志/Hook 合计 100 条/秒、模型/MCP/直连各 1 请求/秒；高负载分别为 400 条/秒、各 5 请求/秒。上游每次模拟 HTTP 请求等待 50ms，模型非流式、PII 关闭。

十个真实签名的 Registry Skill，每客户端十条初始待审计用量，每 20 个工具调用对附带一次 Skill 证据。Skill 用量列表和 `/api/v1/dashboard/overview` 各 1 请求/秒，经过真实管理员认证；列表核对十条种子用量。每类历史数据 10,000 条，保留生产清理实现和预算，只将首次清理安排在补传开始时。

启动前连续采样 30 秒，要求 CPU 中位数 ≤25%、峰值 ≤35%，可用内存 ≥3GiB，实际 Swapins ≤30MiB、Swapouts ≤10MiB，磁盘空闲 ≥22GiB。运行窗口要求 Swapins ≤128MiB、Swapouts ≤32MiB、可访问外部进程 CPU 中位数 ≤15%、可用内存 ≥2GiB。换页来自 `vm_stat`，与 Pageins 分开。

最终 12 轮正式测试和两轮诊断均通过运行环境检查。最后一轮正式测试首次启动检查的 CPU 中位数为 28.85%，没有开始测量，复查合格后才启动。正式窗口最低可用内存 4.05GiB，最大换入 0.063MiB，换出均为零，外部进程 CPU 中位数为 8.55%–9.56%。没有剔除环境合格但性能不利的轮次。正式轮次交叉执行，无 pytest 并行运行。

## 范围、保留证据与后续边界
