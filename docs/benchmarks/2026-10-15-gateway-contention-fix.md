# 网关尾延迟、采集积压与连接失败复测

本次以 [上一轮连接池修复版](2026-10-15-gateway-pool-fix.md) 为直接对照，继续使用 SQLite WAL、单 Uvicorn worker、默认 5 + 10 数据库连接池。测试均使用临时数据库和合成数据。

本轮完成了概览清理批量更新、清理表间让出执行机会和 MCP 调用内连接复用。低负载尾延迟仅部分改善；高负载仍有积压，100 路上传部分指标劣于上一轮。追加的旧版同机 4 路对照显示本次代码改善了该档吞吐和成功率。

## 定位证据

低负载诊断复现了网关尾延迟：补传和清理窗口模型/MCP P95 为 4.20/4.71 秒。SQL 计时捕获到租约 `BEGIN IMMEDIATE` 最长约 6.44 秒、日志批次首次 INSERT 约 11.40 秒；该轮工作线程排队最长约 189 ms。同步操作已离开事件循环，但不同工作线程仍在竞争同一个 SQLite 写锁。移出事件循环后，请求仍需等待数据库写锁。

进一步测量发现，单次后台清理和概览投影也可能执行 1 秒以上。网关一次请求包含鉴权、租约、轨迹、转发准备及审计等多个数据库阶段，较长的维护事务会反复延后这些阶段。

高负载连接诊断在 HTTP 传输异常的内部异常链捕获到 `ConnectionResetError`（macOS errno 54），部分 MCP 调用还包含 `ConnectionRefusedError`（errno 61）。这是 TCP 建连失败，区别于 HTTP 状态错误及数据库连接池超时。短时诊断中记录到 34 次传输失败；此诊断缩短了阶段时长，用于获取错误链，不作为容量结果。

原 MCP 每个协议步骤创建一个 HTTP 客户端，一次调用会建立三次连接。本地模拟服务器的 `ThreadingHTTPServer.request_queue_size` 为 5，突发连接与小监听队列可能共同影响失败率；仅凭异常链不能确定每次失败的全部原因。

## 实现

- 数据库阶段结束后继续立即归还连接；取消已开始的操作时等待工作线程完成，再释放资源。
- AIDR 清理每表每批至多 500 条，每张有待清理数据的表提交并归还连接后让出执行机会，允许其他任务在表与表之间执行。清理和概览投影的批量、积压间隔、空闲检查周期保持原值，保留期、证据与幂等身份、durable ACK 保持原语义。
- 概览清理对完整过期操作批量查询、汇总扣减计数并删除，避免逐条查询和逐条更新统计。仍有部分证据的操作保留逐条重新核对。回归将批量结果与逐条算法比较，覆盖完整过期、仅删除失败结果及命令计数，并限制 100 条完整过期记录的 SQL 调用次数。
- MCP 初始化、初始化通知、实际调用共用本次调用内的 HTTP 客户端及连接池，结束或异常时关闭。每步仍校验目标地址、协议、响应大小和扫描地址快照；DNS 校验在线程执行。会话与凭据不跨调用共享。

跨进程租约和写入原子性仍由数据库事务保证；本次没有验证多 worker、集群或生产高可用场景。

## 对照方法

三个场景均为 100 个独立客户端身份；每批 10 条日志或 Hook，正文 1,024 字节，fsync 到模拟客户端 outbox，接受匹配的 durable ACK 后删除。每第 10 批故意忽略 ACK，再原样重发。

| 场景 | 日志 + Hook 速率 | 每个网关请求率 | 模拟器上传并发 |
| --- | ---: | ---: | ---: |
| 较低负载 | 100 条/秒 | 1 次/秒 | 4 |
| 高负载、4 路上传 | 400 条/秒 | 5 次/秒 | 4 |
| 高负载、100 路上传 | 400 条/秒 | 5 次/秒 | 100 |

空载基线 20 秒、采集 30 秒、暂停上传调度 20 秒、补传与清理 60 秒、继续采集 20 秒，之后最多等待 120 秒排空；网关请求在排空期间继续。每类预置 10,000 条历史日志、Hook、操作、Pipeline Trace 和 Runtime Trace 事件。上游每次 HTTP 固定延迟 50 ms，MCP 三个协议步骤保持一致；正式复跑保留模拟上游原监听队列。

外部负载、断网时长、正文大小、历史规模、上游延迟、数据库连接池配置、后台批次和轮次间隔保持原条件。清理在表间让出执行机会是本次实现变更。模型隐私/PII 关闭，压测模型请求为非流式；流式资源释放由回归覆盖。

正式三档从同一冻结应用快照串行运行，不启用诊断采样，之后再执行集成回归。模型/MCP 成功要求 HTTP 200 且无协议错误，表中网关延迟只统计成功请求；按请求发起阶段归类。入库数与已确认数可能不同，未确认 outbox 不等同于丢失。

本机 Apple M1 Pro、10 个逻辑 CPU、16 GiB 内存，Python 3.12.9、SQLite 3.47.1。负载生成器、后端与模拟上游共享主机，操作系统缓存、内存压力和其他进程并非硬隔离；不能将单轮数字换算为生产 SLA。客户端为协议与持久化队列模拟，未运行 100 个原生客户端或物理 WAN。

## 最终结果

以下仅使用最终版本的三档完整复跑；延迟单位为秒，统计补传与清理重叠窗口内的成功请求。旧版列来自上一轮正式结果。

| 场景 | 模型 P95：旧 → 新 | MCP P95：旧 → 新 | 已确认记录：旧 → 新 | 未确认记录：旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| 低负载，4 路上传 | 3.954 → 3.227 | 3.774 → 3.181 | 13,020 → 13,020 | 0 → 0 |
| 高负载，4 路上传 | 5.978 → 5.843 | 5.197 → 5.414 | 45,140 → 42,180 | 6,940 → 9,860 |
| 高负载，100 路上传 | 18.662 → 18.836 | 15.116 → 19.808 | 49,900 → 46,380 | 2,160 → 5,660 |

最初尚未修复同步连接池等待的版本，低负载模型/MCP P95 约为 0.970/1.449 秒。当前数值仍高于该低负载记录，不能将本次结果表述为尾延迟已恢复到初始水平。

### 本轮旧版同机对照

共享主机环境有变化，因此在最终矩阵之前，另用上一轮冻结源码完整重跑了高负载 4 路上传档；负载参数和测试脚本与最终矩阵一致。此对照只覆盖该档，不能外推为另外两档的同期旧版成绩。

| 版本 | 模型/MCP P95（秒） | 生成 / 已确认 / 未确认 | 全程模型成功/请求 | 全程 MCP 成功/请求 |
| --- | ---: | ---: | ---: | ---: |
| 本轮旧版对照 | 6.398 / 6.806 | 52,060 / 32,590 / 19,470 | 1345/1351 | 1333/1351 |

旧版本轮对照的模型 500 错误栈和 MCP 审计均出现 `All connection attempts failed`。错误链诊断与 TCP 连接复用回归支持减少连接反复创建的修复方向，生产上游连接稳定性仍需验证。

最终三档没有记录上游连接失败。4 路高负载的两次失败发生在压测端读取网关响应时，记录为 `ReadError`，分别位于持续采集和排空阶段；后端日志无对应异常，MCP 上游错误审计为空，现有证据无法确定具体根因。不能将它们计作成功，也不能将它们归为已定位的上游建连失败。

三档的历史日志、Hook、操作均清理 10,000 条，历史 Pipeline Trace、Runtime Trace 事件及会话均清空；错误 ACK 均为零，关闭后的请求租约均为零。低负载恢复时的 2,010 条积压约 12.71 秒确认完毕，最终全部 13,020 条持久化。

100 路高负载的 AIDR 清理耗时从上一轮约 54.95 秒增加到 141.28 秒，MCP P95 从约 15.12 秒增加到 19.81 秒。这是本次对照的负面结果。表间让出执行机会仍需重新竞争写锁，在大量上传竞争下可能拖慢后台完成时间；这是与实现相符的解释，尚未通过隔离单项变更量化其贡献。

当前证据只能确认本地 100 条/秒场景能够排空，不能确认持续承载 400 条/秒。写锁诊断与高负载剩余积压支持继续减少采集、租约、轨迹和统计链路的写入成本；增加上传并发本身没有解决容量问题。数据库迁移没有纳入本次改动。
