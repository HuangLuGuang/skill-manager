# 网关事务减量与采集批内 SQL 对照

本次在 `RENA-1470` rebase 到 `dev` 的 `eeee22bc312991b64d4c54c8da4fb30c2596a925` 后，保留上一轮连接池、保留期清理及 MCP 连接复用修复，先冻结优化前源码，再实现本轮优化。继续使用 SQLite，没有迁移数据库或改变数据表结构。

**正式三档结果：高负载采集吞吐提高，固定排空策略下最终积压清零，网关 P95 降低；低负载 P95 反而升高。** 不能把数据库操作减少表述为所有场景的尾延迟均已改善，也不能把停止生成后的排空表述为持续 400 条/秒容量达标。

## 本轮实现与约束

- MCP 凭证与 Tool 两级租约在同一个 `BEGIN IMMEDIATE` 事务中获取，任一级限额失败即整组回滚。释放两级租约与最终 MCP 审计共用提交；审计提交失败时独立释放。获取过程中取消请求，会先等获取结束，再清理已提交租约。
- 模型及 MCP 的租约获取按 `expires_at` 统计有效请求。全局过期行删除移至后台，每次最多 500 条，有积压间隔 250 ms、空闲间隔 60 秒。尚未删除的过期行不计入并发限额。
- 日志及 Hook 在写锁前序列化正文并计算摘要；在批次写事务内批量读取策略凭据、查重及插入证据。每条记录仍校验客户端、stream、策略版本及有效序列范围，凭据缓存只在本次事务内使用。
- 日志操作投影按原到达顺序折叠后批量 upsert；Skill 投影批量读取已有身份。Coverage 在原位置应用，Skill 的历史关联不会提前看见同批后续证据。
- 幂等键、逻辑事件身份和 Hook 序号约束不变。冲突回滚整个新批次；证据、投影及批次回执一起提交成功后才返回 durable ACK。重复补传不恢复过期正文。

测得的工作量变化如下，使用与压测相同的正文与策略格式：

| 操作 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 10 条日志批次：数据库驱动调用 | 62 | 9 |
| 100 条日志批次：数据库驱动调用 | 602 | 9 |
| 10 条 Hook 批次：数据库驱动调用 | 41 | 6 |
| 100 条 Hook 批次：数据库驱动调用 | 401 | 6 |
| 每个采集批次提交 | 1 | 1 |
| 普通 MCP 调用写事务提交 | 6 | 3 |

数据库驱动调用指 SQLAlchemy `before_cursor_execute` 观察到的 `execute`/`executemany` 次数；`executemany` 内部仍需写入各行，数字不等于 SQLite 行操作数。该采集样本为连续事件、同一策略凭据、不含 Skill 使用证据。MCP 计数开启 Runtime Trace，凭证 last-used 已热，不包含首次凭证更新时间写入或审批分支。

## 对照条件

两个版本的三档矩阵使用相同脚本、外部负载及清理参数，依次串行运行，测量期间不运行测试。优化前采用本次 rebase 后的即时基线，而非直接引用上一轮不同代码基线的数据。

| 场景 | 客户端身份数 | 日志 + Hook 生成速率 | 每个网关请求率 | 上传并发 |
| --- | ---: | ---: | ---: | ---: |
| 低负载 | 100 | 100 条/秒 | 1 次/秒 | 4 |
| 高负载，4 路 | 100 | 400 条/秒 | 5 次/秒 | 4 |
| 高负载，100 路 | 100 | 400 条/秒 | 5 次/秒 | 100 |

每批 10 条日志或 Hook，正文 1,024 字节；模拟客户端将冻结批次 fsync 到 outbox，收到匹配的 durable ACK 后删除，每第 10 批故意忽略 ACK 后原样重试。空载 20 秒、采集 30 秒、暂停上传调度 20 秒、补传与清理 60 秒、继续采集 20 秒，随后最多等待 120 秒排空；网关调用持续到排空结束。实际生成总量的小差异来自调度边界，不调整速率来对齐总数。

预置历史日志、Hook、操作、Pipeline Trace 和 Runtime Trace 事件各 10,000 条，AIDR 保留期 1 天、历史记录 2 天。三类历史清理在补传时启动，其批量及后续调度保持原值。优化版新增的租约清理也受相同启动门控制，单独记录，不计入三类历史清理完成时间。

后端为单 Uvicorn worker、SQLite WAL、默认 5 + 10 连接池；模型非流式、PII 关闭。模拟上游每个 HTTP 步骤延迟 50 ms，MCP 三个步骤沿用上一轮连接复用，监听队列仍为 5。生成器、后端、上游共用本机 Apple M1 Pro / 16 GiB；不是 100 个原生客户端、多 worker 或物理 WAN 验收。

## 正式三档结果

网关 P95 只统计补传与清理窗口发起且成功完成的请求，成功要求 HTTP 200 且无协议错误。吞吐为该窗口内新增有效 ACK 记录数除以实际窗口秒数，日志与 Hook 合计，重复 ACK 不重复计数。最终积压为生成数减已确认数。

| 场景 | 模型 P95（秒）：前 → 后 | MCP P95（秒）：前 → 后 | 有效 ACK 吞吐（条/秒）：前 → 后 | 最终未确认（条）：前 → 后 |
| --- | ---: | ---: | ---: | ---: |
| 低负载，4 路 | 3.061 → 3.933 | 2.308 → 2.483 | 133.16 → 133.33 | 0 → 0 |
| 高负载，4 路 | 5.567 → 4.504 | 5.830 → 4.083 | 139.47 → 278.16 | 11,580 → 0 |
| 高负载，100 路 | 18.904 → 11.572 | 19.981 → 10.369 | 201.83 → 364.49 | 8,310 → 0 |

低负载吞吐高于 100 条/秒是因为同时消化断网期间积压，不是持续产生了更多记录。其断网时已有的 2,010 条积压从约 12.06 秒确认完毕缩短至 11.40 秒，改善幅度小；正式一轮模型/MCP P95 分别升高约 28.5% / 7.6%。

高负载 4 路的窗口吞吐约提高 99.4%，模型/MCP P95 下降约 19.1% / 30.0%；100 路吞吐约提高 80.6%，P95 下降约 38.8% / 48.1%。提高上传并发仍会明显放大网关延迟，不能把 100 路当作生产推荐值；上传并发是模拟器总额度，尚不是平台或原生客户端配置策略。

优化版高负载在继续采集阶段结束时，4 路/100 路仍分别有 16,390 / 12,400 条未确认，随后才排空。补传窗口吞吐也均低于 400 条/秒输入。因此本次证明了有限时长混合负载下的改进，尚未证明持续高负载无积压。

### 低负载反向复跑

正式轮出现低负载 P95 上升后，保持源码、100 个客户端及全部参数不变，追加 **先优化后版本、再优化前版本** 的一组复跑。两个版本各自的应用摘要与正式轮一致，以下保留全部结果，不挑选最好成绩替换主矩阵。

| 低负载轮次 | 模型 P95（秒）：前 → 后 | MCP P95（秒）：前 → 后 | 最终未确认：前 → 后 |
| --- | ---: | ---: | ---: |
| 正式轮 | 3.061 → 3.933 | 2.308 → 2.483 | 0 → 0 |
| 反向复跑 | 2.308 → 0.918 | 1.947 → 0.766 | 0 → 0 |

补充两组均生成、入库并确认 13,020 条；窗口内模型/MCP 各 60 次全部成功。补充轮 Pipeline / Runtime / AIDR 清理时间分别为：优化前 15.990 / 15.482 / 25.512 秒，优化后 10.099 / 12.516 / 17.663 秒。

**低负载尾延迟仍不稳定，不能确认稳定改善，也不能由第一轮认定稳定退化。** 同一优化版模型 P95 在两轮间从 3.933 秒变化到 0.918 秒。每轮仅有 60 个窗口请求，后端、生成器、上游及其他应用共享主机，写锁竞争和运行时调度也未隔离；这些数据不足以区分各因素的贡献。后续应在隔离环境增加重复测量并记录各数据库阶段等待，而不是调整展示口径消除反向结果。
