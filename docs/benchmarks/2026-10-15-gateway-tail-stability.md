# 100 客户端清理窗口与网关尾延迟复测

本轮继续使用 SQLite，针对写锁等待、模型网关事务和断网补传并发进行优化。测试环境为本机隔离数据库和模拟上游。

## 等待来源

独立诊断运行将连接池、线程队列、写锁获取、SQL 和物理提交分别计时。一条采集保存阶段耗时约 2,019 ms，其中写锁获取约 2,006 ms；模型网关准备 Trace 阶段约 2,225 ms，其中写锁获取约 2,219 ms。另一次并发名额获取的 worker 执行约 2,948 ms，其中显式 `BEGIN IMMEDIATE` 约 2,942 ms，线程排队约 1.33 ms。

该诊断运行中连接池获取最大 24.63 ms，线程排队最大 49.02 ms，物理提交 P95 6.75 ms、最大 118.99 ms。实际 Hook 批量 UPDATE 也观察到 235.83 ms 的墙钟耗时，其中线程 CPU 118.06 ms。因此长尾的主要已观察来源是写锁竞争，SQL 工作和提交也有成本。后台统计投影 tick 曾达 988.88 ms，但这个阶段时间包含等待，不能全归因于计算。

诊断探针在首个隐式写入前显式执行 `BEGIN IMMEDIATE`，用于区分获取写锁与 SQL 执行时间，会改变事务插桩方式。下面正式对照全部关闭诊断，不把插桩结果当作性能对照。

## 实现及语义

- 模型网关将完成时的 Runtime Trace、Gateway Session 和非流式请求名额释放合并提交。普通 AccessToken 非流式请求的写提交从 6 次降到 4 次；旧 LlmApiKey 路径因 last_used 写入为 7 次降到 5 次。测量条件为 Runtime Trace 开启、PII 关闭。必要请求审计、用量和 Pipeline Trace 仍先独立提交；可选 Trace 失败会回滚该阶段并由 finally 释放名额。流式请求的名额仍保留到流关闭。
- 日志和 Hook 持久化共用每服务事件循环两个名额的异步入口。排队阶段不占 worker 线程或数据库连接；取消等待中的请求不写库，已经进入 worker 的任务完成后才释放名额。凭据、策略、请求体、幂等和并发名额校验保持，ACK 仍在持久化提交后返回。跨进程一致性仍由数据库事务保证。
- 清理先选择有界候选；没有候选时跳过 DELETE。删除时复查原有条件，避免候选在两步之间续期后仍被删除。清理上限 500 和调度间隔保持。
- 统计投影批量写证据、每组 50 个调用批量读取关联证据并合并桶计数净变化；每个调用最多读取 34 条证据的保守关联边界保持。每来源 250 条上限及调度保持，证据、计数、操作和水位仍同一事务。过期删除在读取投影键前取得写锁，避免与投影交错产生孤立统计。

250 个独立 Hook 调用的隔离微基准：SQL 驱动调用数从 1,512 降到 38。三次完整 advance 耗时为 298.05/350.59/260.77 ms → 111.72/57.88/58.05 ms；首个写 SQL 完成至 commit 开始的区间为 293.66/348.29/258.17 ms → 107.12/55.69/55.75 ms。这是事务内工作区间，不包含物理 commit，不能解释为完整落盘时间。

## 低负载 P95 稳定性

单位 ms，每个单元格对应窗口内 60 个请求；六轮模型和 MCP 均为 60/60 成功。

| 轮次 | 模型基线 | 模型优化后 | MCP 基线 | MCP 优化后 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,588.114 | 903.457 | 1,129.421 | 681.080 |
| 2 | 1,139.551 | 800.391 | 843.133 | 862.090 |
| 3 | 2,132.760 | 911.988 | 1,422.836 | 975.820 |
| 三轮中位数 | 1,588.114 | 903.457 | 1,129.421 | 862.090 |
| 三轮最大值减最小值 | 993.209 | 111.597 | 579.703 | 294.740 |

模型每一对均改善，中位数降低约 43.1%，三轮 P95 极差降低约 88.8%。这是三轮样本的描述，不是置信区间或稳定性 SLA。优化后仍存在秒级单请求尾延迟，例如第二轮模型 P99 约 1,778 ms、最大约 2,415 ms。MCP 中位数降低约 23.7%，第二对从 843 到 862 ms 略有回退，不能宣称所有指标逐轮下降。

优化后第二轮生成 13,100 条，其余低负载轮为 13,020 条；生成速率和阶段配置相同，阶段快照等操作间隙会影响总生成数量。所有记录最终均收到匹配 ACK 并与数据库计数一致，最终 outbox 为零。恢复阶段结束时该轮尚有 20 条未确认，随后排空；不可把最终排空解释为全程无积压。

## 高负载网关与追加复跑

每网关在补传清理窗口各发起 300 次请求，单位 ms：

| 场景 | 模型 P95：前→后 | MCP P95：前→后 |
| --- | ---: | ---: |
| 高负载、4 路 | 2,849.523 → 3,098.645 | 2,596.950 → 3,137.810 |
| 高负载、4 路反向复跑 | 4,001.429 → 2,406.862 | 3,507.502 → 2,198.219 |
| 高负载、100 路 | 12,844.266 → 1,870.999 | 11,121.716 → 1,785.683 |

4 路第一对出现 P95 和补传窗口吞吐回退；模型请求调度延迟 P95 为 2.63 → 152.31 ms，同时记录的预定调度起点到完成 P95 为 2,849.969 → 3,099.801 ms。不能仅以客户端发起偏差解释或排除这次回退。100 路中网关延迟明显改善，单次上传最长约 9.08 秒，仍接近原生客户端 10 秒超时。以上两档结果说明入口并发控制的收益和代价随负载变化。

因首对回退而追加同源码、同参数反向复跑；该对网关 P95、吞吐和积压均改善。两对方向不一致，不能把高负载 4 路写成稳定逐轮改善，也不能仅凭首对判定稳定回退。低负载三对的模型 P95 一致改善是本轮最明确的重复结果。高负载优化后的补传窗口吞吐仍均低于 400 条/s，尚不能据此承诺持续容量。

12 轮均验证最终生成数、唯一 ACK 数、日志与 Hook 持久化数一致，错误 ACK 为零，最终 outbox 为零，请求租约残留为零。预置日志、Hook、操作各 10,000 条均完成过期处理，日志/Hook 过期正文均清空；预置旧 Pipeline Trace、Runtime Trace 事件和会话残留为零。清理循环没有记录错误。
