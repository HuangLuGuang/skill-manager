# 4 路高负载环境排查与重复验证

保持三个回归修复和应用源码不变，减少宿主机干扰后，100 客户端、4 路上传、采集/断网补传/后台清理同时运行的三组对照均完成。保留修复版的补传窗口 ACK 中位数恢复到 533.33 条/s，窗口末未确认 10–20 条；上轮同一源码对应为 429.58 条/s、5,510–7,000 条。此次未复现上轮的持续吞吐下降，当前证据不支持为采集吞吐继续改应用代码；模型网关尾延迟仍未通过不回退验收。

结论仅限此次固定工作负载；SQLite、幂等、并发校验、落盘后 ACK 和三个正确性修复均保留。

## 先核对监控，再控制环境

发现并修正了历史指标名称错误：macOS 上本机 psutil 7.2.2 的 `swap_memory().sin/sout` 来自 Pageins/Pageouts，不能直接当作 Swapins/Swapouts。已通过本机 `vm_stat` 的相同累计数值及 [psutil 对应源码](https://github.com/giampaolo/psutil/blob/release-7.2.2/psutil/arch/osx/mem.c#L100-L101) 交叉核对。上轮报告与结构化结果已改为页面调入/调出命名，保留原始数值；上轮实际交换区读写量无法事后还原。

本轮用 `vm_stat` 的独立 Swapins/Swapouts 乘以本机报告的页大小记录实际交换流量，同时单列 Pageins/Pageouts。不能根据交换区存量较大，或页面调入量较大，就断言正在大量读取交换区。

经用户保存工作并授权，正常退出 Chrome、Termius、Qoder、VS Code 和 Excel。检查发现名为 ChatGPT 的主进程承载本次 Codex 会话，因此保留当前会话及网络代理。空闲可用内存从约 2.9 GiB 增至约 4.5 GiB。首次空闲校准尚未进行任何性能轮次；CPU 稳定底噪约 20%–22%，因此开跑 CPU 中位数门槛由最初 20% 调整为 25%，保留峰值、内存和换页限制，校准记录单独保存。

每轮先采样 30 秒：CPU 中位数 ≤25%、单次采样 ≤35%、可用内存 ≥3 GiB、实际 Swapins ≤30 MiB、Swapouts ≤10 MiB、磁盘空间 ≥22 GiB。条件不满足时只继续空闲检查，不启动测量。运行中每 5 秒记录主机资源及可访问的外部进程 CPU；补传窗口采样需 Swapins ≤128 MiB、Swapouts ≤32 MiB、外部进程 CPU 中位数 ≤15%、可用内存 ≥2 GiB。六轮均通过。

这些是本轮资源检查条件，不是生产 SLA。运行期计数采用窗口内首末样本之差，可能遗漏边缘几个秒；外部 CPU 来自可访问进程，未完整覆盖受权限保护的系统进程。整体 CPU 另行记录。不能用这些检查宣称完成了全系统资源隔离。

## 版本与工作负载保持一致

“前”是上轮三个回归修复前的已优化源码，仅在隔离基准中作为对照；“后”是保留三个修复的当前源码。本轮未改应用代码。两版本与上轮对应源码摘要完全一致，当前工作区也逐文件匹配修复版快照；HEAD 为 `eeee22bc312991b64d4c54c8da4fb30c2596a925`，分支 `RENA-1470` 加既有工作区修改。

100 个客户端身份、4 路上传、日志/Hook 每批 10 条、正文 1,024 字节、生成 400 条/s；模型/MCP/直连各 5 请求/s。单 Uvicorn worker、SQLite 3.47.1 WAL、默认 5+10 连接池、采集并发名额仍为 2。模拟上游每 HTTP 请求 50 ms，非流式模型请求且 PII 关闭。每类历史数据 10,000 条，清理预算及生产调度不变。

每轮：基准 20 s、采集 30 s、断网 20 s、补传与清理 60 s、恢复 20 s，之后最多排空 120 s。客户端 outbox 执行 fsync，故意忽略每十个成功 ACK 中的一个，再按同字节重传。三组顺序为前/后、后/前、前/后，串行运行，正式测量不与 pytest、微基准或诊断插桩并行。除临时端口外，逐项核对所有参数及源码摘要与上轮完全一致。

ACK 指唯一持久化 ACK 记录数；补传窗口同时追赶约 8,000 条断网积压和约 24,000 条新增记录，所需均值约 533.3 条/s。达到该值表示能在此负载下追平积压。窗口末未确认包括已提交但 ACK 尚在途的记录；最终排空另行核对。

## 吞吐下降的直接机制与因果边界

从上轮请求起止时间重建 HTTP 在途数，修复版两轮约 96.9%–97.0% 的补传窗口同时占满四个上传名额。上轮日志请求平均耗时 87–103 ms、Hook 约 72–79 ms；名额长期占满时，请求耗时增加直接压低单位时间完成的上传量，导致新记录与断网积压无法在窗口内全部确认。四路是客户端上传并发，不是服务端同时写 SQLite 的线程数。

当前同一修复版的四名额同时在途比例为 74.0%–77.6%，各轮基本追平积压。这是客户端请求区间的估算，不包含名额内少量外围处理，也不能区分服务端 SQL、锁等待、调度及网络处理各自耗时。

已确认：退出授权应用后，资源观测更稳定，同一应用源码和负载下，两版本均恢复到接近窗口所需吞吐；三组对照未复现修复版持续吞吐下降。合理推测：先前宿主机 CPU/页面调入竞争放大请求耗时，是上轮积压的重要影响因素。尚不能验证：具体哪个应用、CPU 调度、文件缓存或磁盘等待各占多少，历史窗口实际交换流量多少。

没有稳定复现可归因于业务代码的采集吞吐下降，因此本轮只修正测量解释与文档，保持应用实现。为吞吐进一步改写事务或扩大上传并发没有由此次证据支持的必要性。模型网关 P95 的成对升高需要另行分离等待来源；目前不能将它归因于三个修复中的某一处，也不能宣称它已被环境调整解决。
