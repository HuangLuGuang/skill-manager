# Skill 审计与列表短事务：100 客户端混合压测

本次把 Skill 认证计算移到本组首个写入之前，并对列表核对结果分组提交。两组环境合格的高负载对照均改善了采集吞吐、窗口末积压和网关 P95；低负载两组模型网关 P95 也下降。但列表 P95 改善不稳定、概览查询 P95 升高，周期审计积压仍未解决，因此不能宣布所有性能指标通过验收。

数据库仍为 SQLite，保留实时核对、证据并发比较、幂等及落盘后 ACK。此次没有迁移数据库、提交代码或部署。

## 变更与一致性边界

- 后台每批最多 50 条，先计算本批认证，再保存核对结论、历史和告警；调度仍为本轮完成后等待 1 秒，默认每条 30 秒复核。
- 列表每组最多 25 条，计算本组后写入并提交，再处理下一组；保留最多检查 200 条、筛选、分页游标和检查计数。失败组整体回滚，已经提交的组保留。
- 写入时同时比较原始证据内容和未到期条件；并发新证据或清理发生时，旧结果不覆盖新状态，也不据此创建旧告警或历史。认证缓存仅限本次请求或后台轮次，下一次核对重新读取审批、撤销等状态。
- 单条详情及观察结果处理仍由原调用方管理事务。API 权限依赖、采集事务、ACK 和网关并发租约没有调整。

对照基线是本轮改动前的工作区，已包含此前三个并发回归修复及 Dify Session 修复。分支为 `RENA-1470`，HEAD 为 `eeee22bc312991b64d4c54c8da4fb30c2596a925`，另有既有未提交修改。逐轮源码摘要核验一致，前后应用文件仅 `backend/aidr_skill_usage.py`、`backend/routers/aidr.py` 不同；压测脚本在两边相同。

## 工作负载与测量口径

延续原 100 客户端身份、4 路上传、每批 10 条、正文 1,024 字节、客户端 outbox fsync、忽略部分成功 ACK 后按相同字节重传的场景。每轮为基准 20 秒、持续采集 30 秒、断网 20 秒、补传与清理 60 秒、恢复 20 秒，之后最多排空 120 秒。每类历史数据 10,000 条，生产清理实现和预算保持。

新增十个实际签名的 Registry Skill、每客户端十条待认证用量，共 1,000 条初始用量；日志和 Hook 每 20 个工具调用对中有一对附带真实摘要的 Skill 文件证据。Skill 列表和后台概览各 1 请求/秒，通过真实管理员认证访问；列表响应检查十条种子用量的认证结果。后台使用生产认证与审计任务。新增用量数量也与生成数核对。

低负载日志/Hook 合计生成 100 条/秒，模型/MCP/直连各 1 请求/秒；高负载分别为 400 条/秒和各 5 请求/秒。单 Uvicorn worker、SQLite WAL、原连接池和两个采集名额不变，上游模拟每请求 50ms，模型非流式且关闭 PII 处理。

下表指标均来自 60 秒补传与清理窗口。ACK 吞吐是唯一持久化 ACK 增量除以窗口时长，包含追赶断网积压；窗口末积压包含 ACK 在途记录。页面 P95 是 HTTP 请求耗时，不含浏览器渲染；每类页面每轮约 60 个样本。高负载需约 533 条/秒才能在窗口内同时消化新增记录与约 8,000 条断网积压，本次优化版仍未达到这一目标。

共运行 10 个正式轮次和 2 个独立诊断轮次。低负载 `low_2` 的基线补传窗口发生 190.53MiB 实际 Swapins，超过预设 128MiB 门槛；整组成对数据保留，但不纳入收益汇总，另补 `low_3`。有效汇总为低负载、高负载各两组成对结果，取各轮指标的中位值，不是合并请求后重新计算 P95。

每轮启动前采样 30 秒，沿用 CPU 中位数 ≤25%、峰值 ≤35%、可用内存 ≥3GiB、Swapins ≤30MiB、Swapouts ≤10MiB、空闲磁盘 ≥22GiB 的门槛。运行窗口要求实际 Swapins ≤128MiB、Swapouts ≤32MiB、可访问外部进程 CPU 中位数 ≤15%、可用内存 ≥2GiB。未通过启动检查的窗口没有开始测量；检查记录全部保留。有一次程序因连续三次启动检查失败退出，环境恢复后续跑。除上述 `low_2` 基线外，其余正式与诊断运行均通过窗口检查。

Swapins 来自 macOS `vm_stat`，与 Pageins 分开记录。上述门槛用于减少环境干扰；测试使用共享宿主机。源码固定、轮次交叉顺序，正式测量期间未运行 pytest。

## 审计积压与清理

“待复核”含定时复核已到期的历史记录，不等同于尚未首次认证；“最老超期”从 `next_check_at` 起算。每 2 秒采样一次，下表的 P95 是窗口内样本分布。

| 轮次 | 待复核数 P95 | 最老超期 P95 s | 窗口末首次未核对数 | 复核单轮 P95 ms | AIDR 清理 s |
| --- | ---: | ---: | ---: | ---: | ---: |
| low_1 | 116.0 → 112.8 | 2.34 → 2.81 | 0 → 0 | 161.8 → 182.1 | 12.36 → 11.91 |
| low_2 | 120.0 → 125.1 | 2.28 → 2.62 | 0 → 0 | 151.2 → 223.2 | 12.72 → 12.12 |
| low_3 | 128.8 → 126.4 | 2.62 → 2.90 | 0 → 0 | 231.3 → 153.5 | 13.62 → 12.20 |
| high_4_1 | 489.6 → 574.1 | 10.34 → 11.18 | 110 → 121 | 538.4 → 464.9 | 15.38 → 12.92 |
| high_4_2 | 510.1 → 594.5 | 10.23 → 10.77 | 192 → 134 | 1040.3 → 325.1 | 19.05 → 13.75 |

高负载复核单轮 P95 中位值 789→395ms，但待复核数 P95 500→584，最老超期 P95 10.28→10.98 秒。日志最终排空时，两版本的高负载正式轮次均仍有 200 条未首次核对记录；优化版最老超期约 15.1–16.3 秒。本测试没有继续等待审计清空，因此不能宣称所有审计最终完成。

已确认后台仍每轮最多 50 条，之后等待 1 秒；高负载最终有 2,400 条活动用量，仅按 30 秒定期复核便需要约 80 次核对/秒，超过后台任务的理想处理上限。页面也会核对部分用量，但本负载每秒只查十条种子用量。短事务改善了等待，却没有解决复核调度容量。采集更快会更早送入审计任务，也会影响待复核数量，不能仅凭数量把全部差异归因于审计代码速度。

AIDR 清理中位值低负载 12.99→12.05 秒、高负载 17.22→13.33 秒。高负载 Runtime Trace 为 9.34→10.64 秒，Pipeline Trace 为 9.69→7.54 秒；并非所有清理任务都更快，完整结果保留在结构化文件中。

## 独立写锁诊断

单独的一组高负载诊断通过环境检查。插桩在首个隐式 DML 前显式获取写锁，以拆分等待和事务处理；这会改变测量开销，不能将诊断轮次的吞吐/P95 混入正式汇总。“持锁处理段”从拿锁成功到提交/回滚开始，物理提交单列；不同分布的 P95 不能直接相加。

| 路径 | 获取写锁 P95 ms | 持锁处理段 P95 ms | 物理提交 P95 ms |
| --- | ---: | ---: | ---: |
| Skill 后台复核 | 1190.72 → 524.68 | 124.51 → 48.97 | 14.28 → 14.39 |
| Skill 列表 | 295.84 → 160.78 | 72.11 → 16.26 | 16.50 → 15.64 |
| 日志采集 `save_batch` | 162.55 → 128.89 | 12.95 → 13.68 | 9.33 → 6.24 |
| Hook 采集 `save` | 157.39 → 111.30 | 10.61 → 11.35 | 4.71 → 5.26 |

后台和列表持锁处理段分别下降约 60.7%、77.5%，拿锁等待分别下降约 55.9%、45.7%。回归测试也直接验证认证计算期间另一 SQLite 写者可以成功进入，支持“把计算移出写锁范围”的机制。不过其他路径并非全部下降，例如 MCP 完成阶段拿锁 P95 277.60→382.61ms；完整标签和样本数量见 JSON。单组插桩结果用于定位机制，不能证明所有负载下的尾延迟稳定性。

## 正确性验证与边界

相关测试最终 **90 passed**，耗时 33.49 秒。新增测试覆盖后台/真实列表调用路径不在认证计算期间持写锁、35 条跨组分页、200 条筛选检查预算、下一请求撤销/恢复认证、并发新证据/到期保护、批内失败原子回滚，以及列表后组失败保留已提交组。

```bash
  tests/test_aidr_skill_review.py tests/test_aidr_skill_policy.py tests/test_aidr_lifecycle.py \
  tests/test_performance_correctness.py tests/test_aidr_batch_sql.py --tb=short
```

12 轮均无记录到的 HTTP/传输、列表认证响应、后台审计或清理错误。日志与 Hook 最终数量逐轮等于生成预期；错误 ACK、剩余 outbox、请求租约和 running 网关请求均为零；新增 Skill 用量数量吻合。三类历史 AIDR 正文及 Pipeline/Runtime Trace 清理核验通过。这些检查不等同于证明所有 Skill 已完成认证。

本轮真实签名工作负载使用现代 Registry 摘要路径，列表每次返回十条种子记录；大于 25 条的分组行为由回归测试覆盖，其性能未在本负载单独测量。未覆盖旧数据的大目录散列、真实 100 个 Go 客户端、WAN、浏览器渲染、PII、流式模型或多 worker。两个有效对照/负载和每轮 60 个页面样本不足以给出生产容量或严格非劣结论。

受影响 UI 为客户端 Agent 会话的 Skill 审计列表及其详情。未改前端代码、未新增 UI 单元测试。人工 Todo：中英文切换下刷新/筛选/连续翻页；审批撤销和恢复后刷新状态及告警；并发新证据或记录到期时检查列表与详情；观察概览加载耗时。

后续优化应优先定位概览请求的等待来源，并单独设计有时间预算的审计追赶调度；本次数据不支持仅凭缩短事务就宣布周期审计容量问题已解决。
