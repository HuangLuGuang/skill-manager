# 100 客户端采集积压与上传波动复测

本轮保留 SQLite，在上一轮网关事务与统计投影优化之上，减少正文校验及固定 SQL 构造与编译的 CPU 开销。以下为本机隔离数据库和模拟上游的结果，未部署到生产。

14 轮正式对照的结论：四组高负载的补传窗口末未确认量从 1,840–3,720 条降至 10–20 条；三组低负载模型网关 P95 均下降，中位数降低 37.4%。这支持保留本次采集开销优化，但没有解决所有尾延迟问题：4 路高负载的模型/MCP P95 两组均回退，100 路一组改善、一组回退；低负载 MCP 的三轮极差扩大。全部记录最终获得匹配 ACK，另有 1 次采集 `ReadError` 经重试恢复，不能报告零请求错误。

## 定位证据与实现

独立基线诊断中，Hook / 日志保存 worker 的平均线程 CPU 为 7.89 / 9.77 ms，平均墙钟耗时为 32.68 / 36.02 ms；申请写锁阶段的平均墙钟耗时为 20.76 / 22.08 ms，最大为 2,119.16 / 1,518.53 ms。线程排队均值约 0.55 / 0.51 ms。因此长等待集中在写锁申请阶段，不能仅由处理正文的 CPU 时间解释；该阶段包含 SQLite 忙等待及线程恢复调度，不能把全部墙钟时间都视为纯锁等待。诊断在首个隐式写入前显式申请写锁，并对部分 worker 抽样启用 profiler，存在插桩影响，未混入正式性能对照。

进一步用与压测相同的 1,024 字节正文、每批 10 条的样本分析保存阶段，发现正文控制字符校验逐字符调用 Python：100 批日志及 100 批 Hook 各产生约 102 万次检查。Profiler 会放大这类细粒度函数调用成本，不能用其耗时比例直接估算生产收益。

不启用 profiler、交替顺序的三组微基准中，每通道每次写入 100 个新批次（1,000 条记录），SQLite WAL。日志保存线程 CPU：723.64 / 715.82 / 712.57 ms → 714.32 / 672.82 / 684.22 ms，中位数下降约 4.4%；Hook：525.10 / 492.67 / 506.76 ms → 473.06 / 467.16 / 515.65 ms，中位数下降约 6.6%。日志三对均下降，Hook 两对下降、一对回退；这是隔离保存函数指标，混合负载收益以下面的正式对照为准。

- 正文及行为摘要复用预编译正则，替代逐字符 Python 循环；U+0000–U+001F 中仍仅允许制表符和换行，其他字符的接受范围保持。UTF-8 字节上限、采集范围及敏感信息检查保持。
- 批次回执、日志及 Hook 证据插入、日志操作批量 UPSERT 通过 SQLAlchemy `lambda_stmt` 复用固定结构及编译结果；每批值仍独立绑定，默认接收时间按次生成，约束和数据查询仍在数据库执行。原语句在隔离验证中连续三次为 `NO_CACHE_KEY`，新语句为 `CACHE_MISS/CACHE_HIT/CACHE_HIT`，参数、时间默认值和冲突返回值均保持。机制说明见 [SQLAlchemy 官方文档](https://docs.sqlalchemy.org/en/20/core/connections.html#using-lambdas-to-add-significant-speed-gains-to-statement-production)。
- 日志与 Hook 保留原有两个异步采集名额，每批独立校验和提交；网关及后台清理保持原执行路径。身份/策略/序列校验、幂等、并发租约和提交后 ACK 语义保持；数据库、索引及事务边界均未修改。

应用修改限于 `backend/aidr_content.py`、`backend/aidr_behavior.py`、`backend/aidr_hooks.py`、`backend/aidr_operations.py`、`backend/routers/aidr.py`。SQL 缓存复用语句结构，每批执行时仍访问数据库并执行约束；身份、策略和业务查询结果没有跨请求缓存。

在已含正文优化的版本之上，三组无 profiler 的保存函数微基准中，日志 CPU 为 697.20 / 676.98 / 682.95 ms → 621.23 / 617.75 / 616.46 ms，中位数进一步下降约 9.5%；Hook 为 488.43 / 470.49 / 481.26 ms → 445.08 / 453.21 / 445.77 ms，中位数进一步下降约 7.4%，两通道三对均下降。此对照只隔离 SQL 缓存的额外收益；正式混合负载仍与本轮开始前的完整基线比较。

另在两个对照版本中使用相同的 SQLAlchemy 事件记录，测量批次回执 INSERT 成功（确认事务已开启）到提交调用前的线程 CPU；每通道每次 100 批。日志三对为 321.81 / 330.01 / 332.38 ms → 293.05 / 276.40 / 279.31 ms，中位数下降约 15.4%；Hook 为 162.95 / 168.26 / 176.06 ms → 162.69 / 151.33 / 158.55 ms，中位数下降约 5.8%。这是已取得写锁后的一段处理开销，排除了首次锁申请和实际提交/fsync，不能等同于完整持锁时间或并发锁等待。两端使用相同事件插桩；正式轮关闭这些插桩。

## 对照条件

基线为上一轮最终冻结源码，应用清单 207 个文件，SHA-256 `342186eef0bd2d0aca88bb981b30f11a804b2b9776f30b2d35b545858173d1a2`。本轮最终版本同为 207 个文件，SHA-256 `5f098b8ef73edab1074506450879504669aa5279e8db77e7f289bc564a24d5eb`；相对基线 5 个应用文件变化。分支 `RENA-1470`，HEAD `eeee22bc312991b64d4c54c8da4fb30c2596a925` 加工作区修改。

本轮低负载参数与上一轮最终对照一致；同一冻结基线在本轮的延迟明显低于历史测量，因此收益只按本轮交错运行的基线计算，不跨轮次选取较慢的历史数据。

Apple M1 Pro / 16 GiB，单 Uvicorn worker，SQLite WAL 与默认 5+10 连接池；每轮新建隔离数据库、100 个客户端身份。日志和 Hook 每批 10 条、正文片段 1,024 字节。低负载生成 100 条/s，上传并发 4，模型/MCP/直连各 1 请求/s；高负载生成 400 条/s，上传并发分别为 4、100，模型/MCP/直连各 5 请求/s。

每轮：基准 20 秒、正常采集 30 秒、断网 20 秒、补传与清理 60 秒、恢复 20 秒，之后最多排空 120 秒。日志、Hook、操作、Pipeline Trace 和 Runtime Trace 事件各预置 10,000 条历史记录；历史采集数据预先完成投影。真实清理循环首次启动门控在补传开始，其后保持生产间隔及 500 条清理、250 条投影预算。模拟上游每次 HTTP 延迟 50 ms，MCP 三步请求、连接复用、监听 backlog 5；非流式模型请求，PII 关闭。客户端 outbox 执行 fsync，每十次成功 ACK 故意忽略一次并按原字节重放。

低负载三对，高负载 4 路及 100 路各两对，共 14 轮；顺序为高负载 4 路第一对后/前、低负载第一对后/前、低负载第二对前/后、低负载第三对后/前、高负载 4 路第二对前/后，高负载 100 路后/前、前/后。正式轮关闭诊断，不与测试或微基准并行；未隔离宿主机其他进程，也未控制文件系统缓存，因此参数匹配不代表宿主机状态完全相同。P95 统计补传清理窗口发起的成功请求，错误单列；吞吐是该阶段唯一持久化 ACK 增量除以实际墙钟时间。恢复结束未确认量与最终排空分开统计，未确认量可能包含已提交但 ACK 尚在途的记录。

## 完整性与边界

14 轮均已核对源码摘要与每对负载参数；最终日志/Hook 落库数与预期相等，待确认量、残余 outbox、错误 ACK 和残余请求租约均为零。每轮预置的日志、Hook、操作各 10,000 条完成到期处理，日志与 Hook 到期正文清空；Pipeline Trace、Runtime Trace 事件及会话均清理完毕。清理任务没有报告错误。

所有阶段的模型、MCP、直连请求均未记录错误，也未发现 MCP 错误审计。`after/high_100_1` 的 `steady` 阶段日志上传有 1 次 `ReadError`（该阶段 702 次请求中 701 次成功），其余正式轮未记录请求错误。失败记录保留在统计中，驱动重试后最终全部确认；该失败耗时约 54.43 ms，后端日志未找到对应异常堆栈。正式轮仅记录异常类名，无法确认底层连接中断原因，也不能将其归类为网关上游连接失败。

最终回归测试 324 项通过，覆盖控制字符与 Unicode 边界、UTF-8 字节上限、敏感信息检查、SQL 缓存命中后的独立参数与默认时间、批次冲突、幂等重复、提交失败、取消、并发租约、网关及过期投影竞争；未修改 UI。

这次没有实际运行 100 个 Go 客户端或物理断网，也未验证真实 WAN、PII 开启、流式网关、多 worker 和生产磁盘。驱动请求超时 35 秒，不等于原生 Go 客户端的 10 秒超时验证。

## 补充试验与环境异常

结构化结果的 `trial_*` 保留前期探索，未计入本节 14 轮正式比较。固定 SQL 缓存的微基准单独与已含正文优化的版本对照，避免把两项收益混为一项。

首次 100 路基线运行中，本机数据卷耗尽，出现 `No space left on device`，且驱动生成速率下降。该轮中断，连同其已完成的配对优化版均不计入正式比较；完成诊断与校验结果归档后，删除本次探索生成的临时数据库，恢复约 31 GiB 空间，并完整重跑两对 100 路。每轮重跑前均要求至少 20 GiB 空间，检查记录与中断日志单独保存。其余已完成正式轮的请求、记录数量与错误均另行核验；没有把中断轮当作性能退化或数据完整性通过的证据。

此前十轮没有逐轮磁盘余量记录；实际生成量正常、直连 P95 约 62–64 ms，且没有请求错误，但这不足以量化剩余空间对这些轮次的影响。有效高负载各轮最终生成 52,060–52,080 条，低负载各轮 13,020 条；各阶段实际生成速率、驱动延迟和资源样本摘要保留在结构化结果中。
