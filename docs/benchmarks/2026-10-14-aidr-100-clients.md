# 100 客户端采集、补传、清理与网关混合压测

## 测试口径

本次使用独立临时数据库及固定源码快照，运行完整 Backend 的 HTTP、凭证、License、AIDR 接收、网关和后台任务链路。没有迁移数据库，也没有对现有业务数据库施加负载。

- 本机：Apple M1 Pro，10 个逻辑 CPU，16 GiB 内存，macOS 27.0 arm64；Python 3.12.9、SQLite 3.47.1，单 Uvicorn worker、SQLite WAL。负载生成器、后端和模拟上游共用本机，不能直接换算成部署主机容量。
- 100 个独立客户端身份、凭证、采集流及磁盘 outbox。每批包含 10 条日志或 10 条 Hook，包含调用/结果配对，每条正文 1,024 字节。高负载每客户端每 5 秒各生成一批，两条通道共 400 条记录/秒。
- 模型及 MCP 使用固定每次 HTTP 请求延迟 50 ms 的模拟上游；模型隐私/PII 策略关闭。MCP 保留实际多次 HTTP 握手。两个网关各按固定频率发起请求，另以相同频率直连模型模拟上游作对照。每个网关共用一个测试凭证，并发上限为 100。
- 各阶段：网关基线 20 秒、持续采集 30 秒、暂停上传但持续生成 20 秒、恢复上传并触发清理 60 秒、继续采集 20 秒；随后停止生成并最多等待 120 秒排空。以实际请求数及时间戳统计，包含阶段边界请求和停止生产者的收尾时间。
- 每个客户端顺序上传；不同客户端并行。每第 10 个批次故意忽略一次成功 ACK，再原样重发；只有 `durable=true`、摘要及记录数均一致才删除本地批次。
- 预置各 10,000 条历史日志、Hook、AIDR 操作、Pipeline Trace 和 Runtime Trace 事件，预先完成日志/Hook 概览投影。仅控制三类清理任务的首次启动时刻，使其与补传重叠；清理实现、批次上限和后续调度保持生产代码。
- 断网由模拟器暂停上传实现，已经发出的请求可以完成。这不是 100 个原生 Go 客户端，也没有物理断开网络；客户端原生采集、进程重启恢复、真实 WAN、流式模型响应、完整 PII 检测和长期运行不在本次覆盖中。

工作区存在其他并行改动，因此每轮复制固定应用源码。正式对照使用同一组 203 个应用文件，其路径与 SHA-256 清单的规范化摘要为：

`ff28a8f6290481c25520df1aae3b6206c96757ef6f522fb0699a777683e29408`

早期准备试跑受到 macOS 系统代理对本地 MCP 域名的干扰，已排除在结果之外。正式轮次显式设置代理绕过。两客户端协议冒烟曾验证 240 条记录完整入库、重复 ACK 重放去重和全部预置清理完成；它仅用于校验脚本，不作为 100 客户端容量证据。

## 实测结果

**结论：会影响网关。当前代码在高负载下出现连接池阻塞；较低负载可以完成采集、补传和清理，但网关尾延迟仍显著增加。不能把“100 个客户端”本身当作固定容量指标。**

三轮均为 100 个客户端，应用代码相同。上传并发限制在模拟器中实施，尚不是平台或原生客户端已有的生产保护策略。

| 场景 | 日志 + Hook 生成速率 | 每个网关请求率 | 上传并发上限 | 已确认 ACK / 生成记录 | 实际新增入库记录 | 截至结束未确认记录 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 高负载 | 400 条/秒 | 5 次/秒 | 100 | 700 / 52,040 | 820 | 51,340 |
| 高负载、限制上传并发 | 400 条/秒 | 5 次/秒 | 4 | 1,630 / 52,220 | 2,170 | 50,590 |
| 较低负载、限制上传并发 | 100 条/秒 | 1 次/秒 | 4 | 13,020 / 13,020 | 13,020 | 0 |

入库数大于已确认数，表示部分批次已经提交，但客户端没有完成 ACK 确认，仍保留在 outbox 等待重试；不能把这些记录称为丢失。两轮高负载在停止生成后等待了 120 秒，仍未排空。所有收到并接受的 ACK 摘要、记录数及 durable 标志检查均通过。

### 高负载下的网关故障

| 阶段 | 模型成功 / 请求 | MCP 成功 / 请求 | 说明 |
| --- | ---: | ---: | --- |
| 高负载轮次的空载基线 | 101 / 101 | 101 / 101 | P95 分别为 212 ms、482 ms |
| 开始 400 条/秒采集 | 3 / 150 | 1 / 150 | 失败为读取超时或连接失败，读取超时约 35 秒 |
| 补传 + 清理窗口 | 0 / 300 | 0 / 300 | 直连模拟上游 300 / 300 成功，P95 59 ms |
| 限制为 4 路上传后的采集阶段 | 85 / 150 | 79 / 150 | 单独限制上传并发仍未解决阻塞 |
| 限制为 4 路上传后的补传 + 清理 | 0 / 302 | 0 / 302 | 网关仍不可用，直接上游保持成功 |

事件循环采样记录到约 59 秒和 89 秒的停顿。第一轮三类清理均出现一次约 30 秒的连接池超时；两轮高负载截至统计时均未完成历史清理。第一轮分别只处理了 500 条日志、500 条 Hook、500 条操作、1,000 条 Pipeline Trace 和 1,000 条 Runtime Trace 事件；限制上传并发轮次分别为 2,000、2,000、2,000、3,000、2,500 条。

失败请求包含快速连接失败，不能将它们的低耗时解释为延迟改善。网关请求均按发起阶段归类，等待结束后统计结果；截止排空期限而取消的在途上传仍计入积压，但没有进入上传请求的延迟分位。

### 较低负载下的补传和清理

本轮每客户端每 20 秒上传 10 条日志和 10 条 Hook，合计 100 条/秒；模型与 MCP 各 1 次/秒，上传最多 4 路。各阶段请求均成功。

| 阶段 | 模型 P95 / P99 | MCP P95 / P99 | 日志上传 P95 | Hook 上传 P95 |
| --- | ---: | ---: | ---: | ---: |
| 网关基线 | 223 / 417 ms | 376 / 538 ms | — | — |
| 持续采集 | 244 / 429 ms | 635 / 661 ms | 87 ms | 38 ms |
| 补传 + 清理 | 970 / 1,174 ms | 1,449 / 2,147 ms | 890 ms | 675 ms |
| 后续持续采集 | 196 / 199 ms | 402 / 795 ms | 224 ms | 48 ms |

- 恢复上传时有 **2,010 条未确认积压**，约 **14.02 秒**后这一批积压全部收到持久化确认；期间新采集持续进行。
- 最终日志和 Hook 各 **6,510 条**，共 **13,020 条**全部入库，outbox 为空。故意忽略 ACK 后重发 **200 个批次**，没有增加重复记录。
- 历史日志、Hook 和操作各 10,000 条正文全部过期清理；10,000 条 Pipeline Trace、10,000 条 Runtime Trace 事件及其历史会话全部删除。三类清理从首次执行到首次报告无积压分别为：Pipeline **11.78 秒**、Runtime Trace **17.33 秒**、AIDR **25.27 秒**，没有清理异常。
- 采集生成到 durable ACK 的整体 P95 为日志 **15.94 秒**、Hook **24.05 秒**，包含模拟断网及客户端排队时间；上表上传延迟仅从实际发送 HTTP 请求开始计时。
- 模型与 MCP 在补传 + 清理窗口各有 60 个请求，P95 约为空载基线的 **4.4 倍、3.8 倍**。直连上游同窗口 P95 为 **63 ms**，说明新增延迟主要出现在平台侧；这不是单独清理开销的估算，因为补传、采集、投影和清理同时运行。
- 该轮 Backend 峰值 RSS 约 **201 MiB**；CPU 峰值 **108.6%**（psutil 按一个逻辑 CPU 为 100% 计）。数据库文件结束时约 **224 MiB**，WAL 峰值约 **21.7 MiB**。正文清理/删除不意味着 SQLite 文件立即缩小。事件循环记录的最大额外调度延迟约 **431 ms**，没有触发 5 秒阻塞栈采样。

这是约 150 秒阶段负载的有限样本，部分阶段仅 20–30 次网关请求。它验证了本轮数据与特定节奏下的完成性，不是 100 客户端长期 SLA，也不代表现有数 GiB 业务数据库上的结果。

## 已确认的阻塞路径

高负载下捕获到事件循环主线程同步等待 SQLAlchemy QueuePool 的调用栈：

```text
_chat_completions_impl
  -> _acquire_key_slot
    -> request_leases.acquire_lease
      -> Engine.connect -> QueuePool._do_get -> queue.get -> threading.wait
```

限制上传并发的对照还捕获到：

```text
invoke_gateway_with_token
  -> request_leases.release_lease
    -> Engine.begin -> Engine.connect -> QueuePool._do_get -> threading.wait
```

对应代码为 `backend/routers/llm_gateway.py` 的 `_chat_completions_impl`、`backend/routers/mcp_gateway.py` 的 `invoke_gateway_with_token`，以及 `backend/request_leases.py` 的获取/释放租约。它们在异步请求中同步申请数据库连接。AIDR 鉴权与保存之间也保留同一个 Session，并跨越读取请求体及线程调度的 await。

**已确认**：共享连接池等待阻塞了事件循环；后台清理也出现连接池等待超时。阻塞在清理启动之前就已出现，不能把初始故障归因于到期清理。

**代码支持的解释**：请求持有连接跨越异步等待，其他网关调用又同步申请额外连接；连接池耗尽时，事件循环无法继续推进已有请求并释放连接，产生相互等待。仅将清理放到线程执行，不能隔离整个请求链路的连接池竞争。

**不能据此确认**：SQLite 已达到磁盘吞吐上限，或改用某种数据库就能解决问题。本次没有直接测量磁盘 IOPS、单次 SQLite 写锁等待和生产主机长时间稳定性。

## 后续优化顺序

1. 优先处理模型及 MCP 网关获取、释放租约和其他数据库操作中的同步等待，避免它们阻塞事件循环；同时缩短事务与 Session 持有连接的时间，检查额外连接申请。仅把一个函数搬到线程里、或单纯调大连接池，不能据此保证消除相互等待。
2. 将 AIDR 鉴权、写入和提交的连接生命周期收紧，避免请求在等待网络或再次排队时占着数据库连接。为采集和补传配置可观测、有界的准入与退避，再用相同场景验证网关隔离效果。
3. 修复后复跑混合场景，检查生成速率、持久化速率、积压年龄及恢复后的排空时间，而不只看成功请求的平均延迟。后台清理同时检查完成量及失败次数。
4. 在目标部署主机上使用实际日志大小、客户端节奏、数据保留规模和真实上游延迟继续验证，再评估数据库演进。此次没有修改数据库类型或生产配置。

复跑脚本及参数见 [性能脚本说明](../../tests/performance/README.md)。
