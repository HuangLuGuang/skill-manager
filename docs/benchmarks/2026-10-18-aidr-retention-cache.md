# AIDR 到期 UPDATE 成本拆解与交替复测

## 结论与源码边界

以 `RENA-1470`、HEAD `eeee22bc312991b64d4c54c8da4fb30c2596a925` 上包含既有修复的工作区为基线。Git HEAD 不能单独标识本次测试源码，完整文件摘要见[结构化结果](2026-10-18-aidr-retention-cache-results.json)。

确认到期 UPDATE 的成本不只是等待写锁：JSON 表达式索引维护和 SQLite 页缓存压力都贡献了执行成本。临时提高清理连接页缓存预算的候选，在三组交替对照中均缩短了 AIDR 清理完成时间，也减少了高负载补传积压；但高负载模型网关 P95 三组均升高，审计待复核数 P95 三组均升高。吞吐收益不足以抵偿这些变化，未通过整体性能验收。

**最终处置：撤回本轮运行时候选。** 应用文件逐一校验，与本轮起始快照一致；模型网关、数据库和此前各项修复保留。本轮留下测试覆盖与测量证据，不将候选的单项收益描述为当前版本已经获得的提升。下文 `after` 均指已撤回的冻结候选。

## SQL 隔离实验

使用 Python SQLite 3.47.1、WAL、`synchronous=FULL`，在新建临时数据库内保留当前完整表和索引，三类表各 10,000 条历史记录，合成正文约 1 KiB。每个案例到期 1,500 条。删除索引、拆分字段、关闭 spill 的操作仅发生在可丢弃实验副本，未修改应用数据库或迁移。

### 索引与事务粒度

每批 500 条 UPDATE 的中位执行时间（毫秒，不含 commit）：

| 表 | 完整索引 | 去掉 JSON 表达式索引 | 去掉所有二级索引 |
|---|---:|---:|---:|
| 日志 | 17.86 | 9.84 | 7.95 |
| Hook | 49.28 | 11.82 | 8.35 |
| 操作视图 | 38.30 | 18.48 | 8.61 |

这确认索引维护是重要成本，但不能将差值完全解释为 JSON 解析 CPU：索引布局、脏页和访问局部性也同时改变。选中主键的 UPDATE 执行计划、VM opcode 计数和索引定义均已归档。

把正文清除与 `expired_at` 拆成两条 UPDATE，Hook 单批耗时由 49.28ms 增至 70.72ms。把事务拆为 250 条可降低单批成本，但增加提交与重复工作。该候选完成六轮独立混合压测：两组低负载模型 P95 从 308.70/308.06ms 升至 435.24/485.21ms；高负载积压从 4,410 增至 5,310，AIDR 清理从 13.85s 增至 18.95s，因此不再继续该候选。六轮记录全部保留，未混入最终十二轮统计。

### 页缓存预算

保持每批 500 条和原索引，三次重复、每次三个事务，得到以下中位数。临时方案每批提交后恢复原缓存设置；组合时间逐事务计算 UPDATE + commit + 恢复，再取中位数。

| 表 | 默认 UPDATE ms | 临时 8 MiB UPDATE ms | 默认组合 ms | 临时 8 MiB 组合 ms | 恢复设置 ms |
|---|---:|---:|---:|---:|---:|
| 日志 | 17.12 | 13.52 | 27.84 | 23.56 | 0.113 |
| Hook | 48.87 | 28.44 | 79.07 | 62.02 | 0.224 |
| 操作视图 | 37.68 | 22.07 | 60.77 | 48.10 | 0.183 |

另一个三次重复实验中，8 MiB 与 32 MiB 的 UPDATE 耗时接近，未观察到继续增大的明确收益。只在隔离副本关闭 spill 也得到类似改善，支持脏页缓存压力这一解释；**没有直接测量 spill 次数或磁盘块读写次数**，不能声称已经分解每一个 CPU/IO 成本。

SQLite `cache_size` 是每个数据库连接的建议页缓存预算，负值按 KiB 解释，并非一次预分配或严格内存上限。`cache_spill` 控制事务中脏页溢出，两者不能混为业务数据缓存。[SQLite PRAGMA 文档](https://www.sqlite.org/pragma.html#pragma_cache_size)

## 最终候选的测试范围

运行时差异只有 `backend/aidr_retention.py`：非空清理批次执行写入前，将小于 8 MiB 的连接页缓存预算临时提高，保留更大的现有设置；提交、失败回滚、关闭会话后，在连接池 reset 阶段恢复原值。保持每表每批 500 条、提交次数、到期条件复核、日志/Hook 证据扣减、后台调度、鉴权、策略读取、并发限制和落盘后 ACK 不变。

该候选没有修改模型网关、数据库 schema、索引、WAL、`synchronous` 或 spill 开关。连接池 reset 发生在 check-in 前；错误恢复依赖 SQLAlchemy 的连接失效处理。[SQLAlchemy PoolEvents.reset](https://docs.sqlalchemy.org/en/20/core/events.html#sqlalchemy.events.PoolEvents.reset)

## 混合负载条件与环境

- 100 个客户端身份，4 路上传，每批 10 条日志和 10 条 Hook，正文 1,024 字节；低负载每 20 秒一批，共 100 条/秒；高负载每 5 秒一批，共 400 条/秒。
- 模型网关、MCP 网关、直连模拟上游分别为低负载 1 RPS、高负载 5 RPS；模拟上游每次 HTTP 等待 50ms，模型非流式、PII 关闭。
- 每轮依次为网关基线 20s、正常采集 30s、暂停上传 20s、补传与清理 60s、继续采集 20s，最后最多排空 120s。生成继续进行，本地 outbox fsync，每十个成功 ACK 故意忽略一次并重放完全相同批次。
- Skill 审计开启，10 个真实签名 Skill、每客户端预置 10 次使用，每 20 个调用对生成 Skill 证据；Skill 使用列表和 Dashboard 各 1 RPS，使用真实 JWT 鉴权。
- 三类 AIDR 历史表及 Pipeline/Runtime Trace 各 10,000 条；清理首次启动固定到补传窗口，之后使用原生产批量和调度。单 Uvicorn worker，SQLite WAL，独立临时数据库与凭据。
- 十二轮正式顺序：before-low1、after-low1、after-high1、before-high1、after-low2、before-low2、before-high2、after-high2、before-low3、after-low3、after-high3、before-high3。另跑 before/after 各一轮诊断，不计入正式性能结果。
- 每轮启动前取 6 个 5 秒样本：CPU 中位数 ≤25%、峰值 ≤35%、可用内存 ≥3 GiB、换入 ≤30 MiB、换出 ≤10 MiB、剩余空间 ≥22 GiB；补传窗口要求外部 CPU 中位数 ≤15%、可用内存 ≥2 GiB、换入 ≤128 MiB、换出 ≤32 MiB。换入/换出取 `vm_stat Swapins/Swapouts`，不把 Pageins 当作交换。

正式矩阵十二轮全部通过上述环境门槛。保留 Codex 和网络代理；测量期间没有并行运行回归测试或 SQL 隔离实验。

## 独立写锁诊断

两轮诊断均通过环境检查。探针在首个 DML 前显式取得写权限，改变了执行开销，因此只用于解释机制，不纳入十二轮正式吞吐、积压与 P95。诊断窗口有效 ACK/积压与正式窗口明显不同，也证明不能把两者混合。

`write_transaction` 从成功取得写锁计时到 SQLAlchemy commit/rollback 事件触发，**不包含随后 DBAPI commit**；commit 单独记录。以下不是精确的“锁从获取到释放”完整分布，不相加不同指标的 P95。

| 诊断指标 | before | after |
|---|---:|---:|
| AIDR 写事务数 | 60 | 60 |
| AIDR 获锁后、提交前累计执行 ms | 4,169.26 | 3,184.97 |
| AIDR 获锁后、提交前 P95 ms | 133.88 | 114.79 |
| AIDR commit 累计 ms，含无写入的提交调用 | 1,664.65 | 1,934.16 |
| AIDR 等待写锁 P95 ms | 137.04 | 151.33 |
| AIDR worker 排队 P95 ms | 1.03 | 1.19 |
| AIDR 连接池等待 P95 ms | 0.01 | 0.01 |
| Skill 审计等待写锁 P95 ms | 57.89 | 141.09 |
| Skill 列表等待写锁 P95 ms | 122.30 | 221.01 |
| 概览投影等待写锁 P95 ms | 156.80 | 348.34 |
| 概览投影获锁后、提交前累计执行 ms | 4,048.53 | 3,648.01 |

清理提交前累计执行下降 23.6%，但提交累计时间增加 16.2%；两者累计合计约 5.83→5.12s（−12.3%），只可作为该轮占用写阶段成本的近似汇总。剩余的大头包括概览投影，并非全由清理决定。连接池与线程准入排队仍远小于写锁等待。

记录到的 AIDR 主表 UPDATE 每表各 20 次，单条 wall/线程 CPU 中位数为：

| 表 | before wall / CPU ms | after wall / CPU ms |
|---|---:|---:|
| 日志 | 19.79 / 19.69 | 15.01 / 14.29 |
| Hook | 99.41 / 97.85 | 68.95 / 62.93 |
| 操作视图 | 54.43 / 53.09 | 32.43 / 32.11 |

SQL 探针只记录 ≥5ms 的语句，上表恰好覆盖本次每表 20 个主 UPDATE，全部 SQL 总成本尚未统计。日志 UPDATE 还有候选单次 114.88ms 的异常尾部，中位值没有展示这一点，完整分布保留在 JSON。

**已确认：** 清理 SQL 的 CPU/缓存成本可下降，且提交与其他写入者的等待仍显著。**合理推测：** 更快的局部清理改变了共享写入者的交错与竞争，收益没有均匀转化为审计、页面、网关尾延迟。单组诊断不能证明全部尾延迟上升的因果链；尤其诊断轮模型尾延迟反而下降，不足以推翻三组无探针正式对照。

下一步更值得验证共享写入的准入顺序与概览投影持锁，而不是继续单独扩大清理缓存或缩小批次。该方向尚未实施和验证。

## 正确性与最终验证

候选通过 94 项定向测试，包括五种原缓存设置、失败回滚、取消期间提交、失效连接恢复，以及真实后台清理选取后并发上传迟到结果的回归。候选专用测试随候选一起撤出产品测试目录，保存在本地实验目录，供复核候选使用。

最终保留的新增覆盖：将已有迟到结果竞态测试同时运行于同步清理与真实后台 `cleanup_once()` 路径；在选择完成、写入前通过真实 HTTP 接口并发上传结果，检查 durable ACK、新操作视图未误清理、重传幂等和原始过期正文仍被清除。最终状态重新运行相关回归测试，**86 项通过**（35.57 秒）；候选的 94 项与最终的 86 项分别记录，不能把已撤回的八个候选专用用例算作最终产品测试。

## 可验证范围

这些数据来自同一台开发机、三个配对样本，不是生产容量承诺，也不足以给出显著性或长期尾延迟保证。环境门槛降低了干扰，不能证明完全消除了系统噪声。高负载仍有约四千条断网积压；要在 60 秒内同时处理 400 条/秒新数据和约八千条历史积压，需要约 533 条/秒有效 ACK，本轮没有达到。
