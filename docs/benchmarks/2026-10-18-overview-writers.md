# 概览投影持锁与 AIDR 写入等待复测

## 源码及成本定位

基线为 `RENA-1470`、HEAD `eeee22bc312991b64d4c54c8da4fb30c2596a925` 上包含此前所有修复的工作区。逐文件 SHA-256 与上一轮最终保留的应用源码相同；HEAD 本身不能描述这些未提交修改。冻结源码、逐轮数据和环境记录位于 `outputs/performance/2026-10-18-overview-writers-final/`。

源码确认两个独立问题：

1. `advance()` 在取得 SQLite 写权限后才加载原始日志/Hook、解析 JSON、分析命令和构造投影，并在同一写事务内处理两种来源。
2. 原有两个异步准入名额覆盖采集和 Skill 审计；概览投影与 AIDR 清理另行进入线程和 SQLite 写锁竞争。SQLite 仍然只有一个写入者，增加这些等待者不会增加并行写入能力。

新建隔离数据库、保留当前 schema/索引，生成两类各 5,000 条合成证据，运行 20 次、每次每来源最多 250 条的投影。带 cProfile 的局部实验中，基线总时间 2.064s，约 0.567s 用于 `project()`，全部发生在写阶段；证据核对约 1.035s。候选总时间 2.099s，投影准备约 0.558s 已全部移到写阶段之前。

这说明可以缩短写权限占用，但**局部总时间没有下降**，不能把移出锁内的 CPU 时间直接称作吞吐提升。查询、解释器调度和实际写入竞争需要混合测试验证。此实验没有与正式压测并行运行。

## 候选机制及并发边界

应用差异只涉及 `backend/aidr_overview.py`、`backend/aidr_retention.py`、`backend/services/aidr_ingest.py`：

- 两种来源都先读取当前水位、选取原始记录并准备投影。取得写权限后重新读取水位；其他 worker 已推进的来源留待下一轮重新准备，不覆盖已有进度。
- 发布前按本批主键读取当前到期标记与正文是否存在；已经到期或删除的原始记录不发布。事件正文除了到期清除外保持不可变，这是锁外准备成立的前提。
- 当前证据的关联核对、歧义处理、净计数变化和水位仍在一个事务中提交。每来源 250 条和每操作 34 条证据上限保持。
- 概览后台 pass 和 AIDR 清理每个有界步骤加入现有两个异步准入名额，与采集、审计共享。清理每表最多 500 条、独立提交及原重试间隔保持；取消时等待正在执行的数据库 worker 完成后再释放名额。
- 模型网关、数据库 schema/索引、WAL、提交耐久性和权限/策略读取路径没有改动。没有新增权限或策略结果缓存。

首次候选复核写成 `id IN (...) AND expired_at IS NULL` 时，执行计划显示 SQLite 可能选用到期索引。修正后 WHERE 只限定主键，在所选行的结果中检查到期标记，避免扩大扫描范围；回归测试核对实际 `EXPLAIN QUERY PLAN`。修正前的两轮低负载测量单独保存在 `outputs/performance/2026-10-18-overview-writers/`，不混入修正后的正式对比。

## 工作负载及验收口径

沿用此前 100 客户端混合负载：真实 HTTP、单 Uvicorn worker、SQLite WAL，4 路模拟上传，每批日志/Hook 各 10 条、正文 1,024 字节。低负载每 20 秒一批，共 100 条/秒；高负载每 5 秒一批，共 400 条/秒。模型网关、MCP 网关、直连模拟上游分别为 1/5 RPS；上游每次 HTTP 等待 50ms，模型非流式且 PII 关闭。

每轮网关基线 20s、正常采集 30s、暂停上传 20s、补传清理 60s、继续采集 20s，最后最多排空 120s。断网期间继续生成，outbox fsync，每十次成功 ACK 忽略一次后按相同字节重放。三类 AIDR 历史表及 Pipeline/Runtime Trace 各 10,000 条。首次清理固定在补传窗口开始，后续使用生产调度。十个真实签名 Skill、每客户端十条初始使用记录，持续加入 Skill 证据；Skill 列表与 Dashboard 各 1 RPS，经过真实 JWT 鉴权。

每个负载保留三组合格配对。顺序交替：第一轮低负载 before→after、高负载 after→before，第二轮反转，第三轮再反转。环境不合格的整个配对保留在原始结果中，并补跑完整配对；不根据性能好坏剔除样本。诊断轮另行运行，不并入正式吞吐和 P95。

环境门槛与前轮相同：启动前 30 秒、6 个样本，CPU 中位数 ≤25%、峰值 ≤35%、可用内存 ≥3GiB、换入 ≤30MiB、换出 ≤10MiB、剩余空间 ≥22GiB。补传窗口外部 CPU 中位数 ≤15%、可用内存 ≥2GiB、换入 ≤128MiB、换出 ≤32MiB。换入取 `vm_stat Swapins`，不将 Pageins 混为换入。Codex 和网络代理保留，测量期间不运行回归测试或 cProfile。

第一组低负载候选窗口的外部 CPU 中位数达到 17.58%，超出门槛；记录到 `duetexpertd` 额外占用，随后外部占用回落。该轮及其配对基线保留但不进入主汇总。环境门槛通过也不代表消除了系统噪声，三组样本不足以证明长期非劣或生产 SLA。

## 独立诊断及剩余等待

额外各跑一轮高负载诊断，环境均达标，外部 CPU 中位数 11.40% / 11.20%。探针记录首次写入获得权限到物理提交/回滚返回的完整占用，并区分异步准入、线程排队、取连接和获取写权限。探针有额外 I/O，并为隐式事务显式插入 `BEGIN IMMEDIATE`，故以下只用于机制定位，不并入正式性能收益。

| 诊断指标（ms） | 前 | 后 |
| --- | ---: | ---: |
| 概览持锁中位数 / P95 | 74.89 / 177.31 | 54.94 / 112.49 |
| 概览获取写权限 P95 | 148.35 | 65.69 |
| 日志批次获取写权限 P95 | 121.20 | 73.56 |
| Hook 批次获取写权限 P95 | 102.55 | 72.68 |
| Skill 列表获取写权限 P95 | 382.10 | 287.24 |
| AIDR 清理持锁 P95 | 179.89 | 174.62 |
| 采集异步准入等待 P95 | 118.88 | 144.76 |
| Skill 审计异步准入等待 P95 | 173.71 | 163.51 |

概览窗口内完整持锁总量从 4.786s 降至 3.154s（56 / 54 次），与锁外准备的局部实验方向一致。采集线程排队 P95 约 1.1–1.3ms，Dashboard 主函数排队 P95 为 2.24 → 1.96ms，取连接一般低于 1ms；本轮主要瓶颈是写权限竞争，不是线程数量或连接池不足。共享名额将一部分等待提前到异步队列，采集准入等待有所增加，但获得连接后的写锁等待下降。

AIDR 清理单次完整持锁 P95 基本不变；候选新增准入等待累计约 5.13s、P95 142.64ms。因此清理全量完成变慢有明确的调度等待成分，不能解释为 UPDATE 本身加速或单次持锁显著缩短。剩余较长单次占用仍包括 AIDR 清理；采集事务数量多，窗口内两类采集完整持锁合计约 21.4s，也会与网关和其他写入者竞争。

探针在等待开始时看到了概览、清理、其他采集及网关写入者；它只记录 Python 层当时观察到的 owner 标记。物理提交返回与标记清除之间存在极短窗口，可能同时看到多个标记，**不代表 SQLite 同时有多个写入者**。一次等待可能跨过后续多个事务及 busy-handler 重试，不能把等待全量归因于初始标记。

Dashboard 诊断轮未复现正式两对中的变慢：主函数执行 P95 为 183.27 → 153.15ms，线程 CPU P95 为 107.58 → 108.30ms；慢 SELECT CPU P95 约 29.92 → 29.85ms。该路径未记录到写事务，主要耗时在实时读取与响应构造。当前证据不支持“Dashboard 正在等待概览写锁”或“线程池耗尽”的结论。持续入库导致两侧同一时刻已确认数据量不同、CPU 调度和查询缓存变化，均可能影响尾延迟，但本轮没有证明某一项是正式波动的原因；不据此增加缓存或降低权限、策略与计数实时性。

每 5 秒只读采样投影水位：日志 ID 差中位数 455 → 415、Hook 525 → 400；P95 分别 994 → 1,014、1,197 → 1,299。水位更新时间差 P95 约 5.2 → 5.3s，两侧最终 ID 差均为零。ID 差不是任意数据库下的未处理有效记录数；这里为连续生成 ID 的合成负载。未发现持续饥饿，但短时尾部延迟没有全面下降。

## 当前处置与边界

保留本轮三处应用文件的改动：主目标的积压三对均减少，概览持锁缩短，低负载模型和高负载 Skill 列表均有一致改善；未发现功能或证据一致性回归。**性能验收仍是部分达成，不能标记“全部页面与网关无回退”**：页面个别轮次变慢、低负载周期审计数增加、AIDR 完成清理更慢，均作为剩余风险保留。诊断未确认页面波动的可修复原因，因此没有继续叠加推测性调参。

正式 14 轮中 12 轮进入主汇总，另 2 轮作为整对环境排除；独立诊断 2 轮，早期候选探索 2 轮另存。全部完成轮次未出现 HTTP、传输、后台维护或清理错误。生成的唯一记录全部收到 ACK，数据库日志/Hook 数量匹配，错误 ACK、残留 outbox、最终未审计记录和活动租约均为零，历史正文均完成清理。两轮诊断额外核对：不存在已过期或缺失原始记录的投影证据，操作与桶的调用/失败计数一致，命令次数一致。

逐轮指标、环境、源码哈希、诊断与完整性核对见 [机器可读结果](2026-10-18-overview-writers-results.json)。工作区应用文件与冻结候选逐文件哈希一致；模型网关代码、数据库结构和耐久性配置与基线相同。本轮未提交、推送或部署。

## 正确性覆盖

候选通过 **93 项定向测试，37.80 秒**。新增用例覆盖：

- 在准备投影后、获取写权限前，另一个连接完成到期清理：旧证据和计数不能重新出现。
- 同一窗口另一 worker 完成投影：重新检查水位，重试后不重复计数或倒退水位。
- 发布前复核使用本批主键查询，不通过到期索引扫描整个活动集合。
- 两个名额已占用时，概览和清理等待期间不启动数据库 worker。
- 取消概览/清理时，正在执行的 worker 结束前不把名额交给新上传。

相关既有测试同时覆盖并发相同批次、冲突回滚、提交失败不 ACK、迟到结果上传与清理并发、证据歧义/乱序、桶计数、实时认证及策略变更。功能测试通过不等于性能验收通过。
